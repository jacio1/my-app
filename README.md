# Мой дневник

Next.js-приложение для задач, заметок, дневника, планов и целей. Работает локально без аккаунта; после настройки Firebase поддерживает вход через Google и синхронизацию. MCP/API дают помощнику доступ к тем же данным независимо от истории конкретного чата.

## Локальный запуск

```powershell
npm ci
npm run dev
```

Открыть `http://localhost:1001`. Без облачных настроек записи сохраняются в браузере. Для телефона в домашней сети можно использовать IP компьютера и порт 1001, но Google-вход и установка PWA требуют разрешённого origin/HTTPS. Для постоянного использования публикуйте приложение по HTTPS.

## Включить синхронизацию

1. В [Firebase Console](https://console.firebase.google.com/) выбрать существующий проект или создать новый. Добавить Web App.
2. Authentication → Sign-in method → включить Google. В Authorized domains добавить `localhost` и будущий домен сайта.
3. Создать **Cloud Firestore, Standard edition, Native mode**, базу `(default)`. Выбрать регион рядом с пользователями. Не открывать доступ всем через test-mode rules.
4. Скопировать `.env.example` в `.env.local`. Заполнить `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID` из конфигурации Web App. Эти значения являются идентификаторами приложения; доступ к записям защищают Authentication и правила Firestore.
5. Применить `firestore.rules` через вкладку Firestore → Rules, либо через CLI:

   ```powershell
   npx firebase login
   npx firebase deploy --only firestore:rules --project YOUR_PROJECT_ID
   ```

6. Перезапустить приложение. Профиль → «Войти через Google» → «Перенести локальные записи». Повторить вход в тот же аккаунт на другом устройстве.

Применение правил к существующей базе влияет на другие коллекции этого проекта: всё, кроме собственных `/users/{uid}/records`, закрывается для клиентского SDK. Для базы, которую используют другие приложения, сначала объедините правила.

### Как сохраняются данные

- Каждая запись — отдельный документ `/users/{uid}/records/{section}_{encodedId}`. Разделы: `tasks`, `notes`, `diary`, `plans`, `goals`.
- Firestore передаёт изменения в реальном времени и сохраняет очередь офлайн-записей в IndexedDB, включая поддержку нескольких вкладок. Изменяются только затронутые поля. При конкурирующих правках одного поля действует last-write-wins по порядку получения сервером.
- Удаление — синхронизируемая метка `deleted`, чтобы старое устройство не возвращало запись при обычном чтении. Правка той же записи с офлайн-устройства может восстановить её; это ограничение выбранной модели last-write-wins.
- Без интернета можно продолжить работу в **уже открытом приложении**. Холодный запуск офлайн показывает страницу восстановления связи. Полный офлайн-запуск всех экранов в этой версии не реализован.
- Гостевые записи и кэш аккаунта разделены. Вход не загружает гостевые записи автоматически. Перенос добавляет отсутствующие ID и не перезаписывает версии аккаунта; удалённые в облаке записи повторно не переносятся.
- JSON-экспорт содержит все пять разделов. Старые копии schemaVersion 1 читаются без потери задач, заметок и дневника. Новые копии имеют schemaVersion 2. Импорт заменяет **данные текущего режима**, включая облако, если пользователь вошёл; перед импортом скачайте копию. Один пакет ограничен 450 изменениями.
- Офлайн-кэш предназначен для личных устройств. Выход из аккаунта не очищает дисковый кэш и заблокирован при неподтверждённых записях. Для удаления данных с чужого устройства очистите данные сайта в браузере.
- При серверном отказе текущая вкладка сохраняет отдельную копию отклонённых правок (по возможности в localStorage) и предлагает скачать её в профиле. Не очищайте браузер до экспорта. Это аварийная копия, она может содержать старые версии других записей; не импортируйте её поверх облака без проверки.

## Опубликовать сайт

Подойдёт хостинг с Node.js и поддержкой Next.js Route Handlers, например Vercel. **Static export / GitHub Pages не подходят** для API/MCP/OAuth.

1. Импортировать GitHub-репозиторий на хостинг; команда сборки `npm run build`, стандартный Next.js runtime.
2. В секретных настройках хостинга задать Firebase-переменные. `NEXT_PUBLIC_*` нужны во время сборки.
3. Задать `APP_URL=https://YOUR_DOMAIN` — точный постоянный origin, без пути. Он используется в OAuth discovery и проверке Origin.
4. В Firebase Authentication добавить домен сайта в Authorized domains.
5. Применить правила Firestore и выполнить новую сборку/деплой.
6. Открыть сайт на телефоне и ноутбуке, войти в один аккаунт, создать тестовую запись на одном устройстве и проверить её на другом.

HTTPS нужен для service worker и установки. На странице профиля кнопка установки появляется только при наличии поддерживаемого браузерного механизма. В остальных браузерах используется собственное меню установки, если оно доступно. Manifest содержит постоянный `id`, обычные и maskable PNG-иконки. Service worker хранит только общую страницу отсутствия сети, а не дневник, токены или ответы API.

## Подключить помощника из чатов

### Серверная настройка

Для обычной синхронизации достаточно клиентских переменных и правил. Для MCP/API/OAuth дополнительно нужен Firebase Admin:

1. Firebase → Project settings → Service accounts → создать ключ сервисного аккаунта для **этого же проекта**.
2. Установить содержимое JSON одной строкой в секретную переменную `FIREBASE_SERVICE_ACCOUNT_KEY` на сервере. Локально — в `.env.local`, вне Git. Не использовать префикс `NEXT_PUBLIC_` и не отправлять ключ в чат.
3. Перезапустить/пересобрать сайт. Профиль → «Помощник в чатах» должен загружать список подключений без ошибки.

Admin SDK обходит Firestore Rules, поэтому все серверные действия проверяют аккаунт/токен и привязывают запрос к UID владельца. Долговременные токены и коды хранятся только в виде SHA-256-хешей; исходный токен виден один раз. Записи дневника в базе не имеют дополнительного сквозного шифрования, поскольку сервер должен предоставлять их авторизованному помощнику.

### OAuth-подключение (основной способ)

Адрес MCP-сервера: `https://YOUR_DOMAIN/api/mcp`.

Для Codex CLI, поддерживающего MCP OAuth:

```powershell
codex mcp add my-diary --url https://YOUR_DOMAIN/api/mcp
codex mcp login my-diary
```

При подключении открыть страницу разрешений, войти через Google и подтвердить доступ. В поддерживающем пользовательские MCP-подключения ChatGPT добавить тот же адрес; доступность зависит от продукта, тарифа и настроек рабочего пространства. Совместимость с реальными клиентами нужно проверить после публикации — локальный `localhost` недоступен облачному ChatGPT.

Реализованы OAuth authorization-code + обязательный PKCE S256, discovery, регистрация публичных клиентов, одноразовые коды (5 минут), access token (1 час), ротация refresh token и отзыв всего подключения. Разрешения: `records:read` и `records:write`. Подключение живёт 90 дней; после этого требуется повторный вход.

Разрешены callback origins ChatGPT/Codex и loopback HTTP на `localhost`/`127.0.0.1`. Если клиент использует другой HTTPS callback, добавьте **точный origin** в `OAUTH_ALLOWED_REDIRECT_ORIGINS` на сервере. Wildcards не поддерживаются. На экране разрешений отображается полный адрес возврата.

Встроенные ограничения частоты действуют в одном процессе. Перед публичным использованием настройте общие лимиты/WAF на хостинге для `/api/oauth/*`, `/api/mcp` и `/api/v1/*`, особенно регистрации OAuth-клиентов. Просроченные OAuth-документы не очищаются автоматически: настройте периодическое удаление по числовому `expiresAt` или отдельную задачу обслуживания. Не включайте логирование Authorization/токенов/тел дневниковых запросов.

### Подключение по токену

Профиль → «Ручное подключение по токену» → создать подключение (при необходимости только чтение). Сохранить токен в защищённом хранилище клиента. Передавать его заголовком `Authorization: Bearer TOKEN`; не добавлять в URL и репозиторий. Токен действует 90 дней. Кнопка «Отозвать доступ» немедленно блокирует и ручное, и OAuth-подключение со всеми его refresh/access токенами.

MCP-инструменты:

| Инструмент | Назначение |
| --- | --- |
| `list_records` | Читать/искать записи; фильтры `section`, `query`, `date`, `limit` |
| `create_record` | Создать задачу, запись, план или цель; обязательный `idempotencyKey` делает повтор безопасным |
| `update_record` | Обновить запись с проверкой последнего `expectedUpdatedAt` |
| `delete_record` | Удалить по явной просьбе, также с проверкой `expectedUpdatedAt` |

Примеры просьб после подключения: «Прочитай мои задачи и сохрани план на завтра», «Создай цель и запиши этапы», «Добавь в дневник: сегодня…». Помощник получает состояние из базы, поэтому история этого чата не требуется. Подключение должно быть включено в конкретном чате/клиенте; события из других чатов, которые не сохранены в приложение, не появляются автоматически. Модель не встроена в само приложение и не работает в фоне.

### REST API

Все запросы требуют Bearer-токен подключения; UID из тела запроса не принимается.

- `GET /api/v1/records?section=tasks&limit=100`
- `POST /api/v1/records`: `{ "section": "plans", "title": "План на день", "text": "Дела и время", "date": "2026-11-22", "idempotencyKey": "unique-request-id" }`
- `PATCH /api/v1/records/{section}/{id}`: изменяемые поля и `expectedUpdatedAt` из последнего чтения.
- `DELETE /api/v1/records/{section}/{id}`: `{ "expectedUpdatedAt": "…" }`.

План на день использует реальную дату `YYYY-MM-DD`; у плана задачи дату можно не задавать. Все разделы кроме задач требуют непустой текст. У задач/целей есть `completed`. Ограничения: заголовок 500 символов, текст 100 000, выдача до 200 записей, аккаунт до 2000 записей для API этой версии. Конфликт обновления возвращает 409; нужно перечитать запись перед повтором.

## Проверки

```powershell
npm run lint
npm test
npm run build
npm run test:e2e
```

Браузерные тесты используют установленный Microsoft Edge, отдельный порт 3100 и локальный режим без Firebase. Проверяются формы, сохранение после перезагрузки, миграция данных, мобильная навигация, manifest и отказ API без конфигурации.

Для облачных интеграционных тестов нужны Java 21+ и свободные порты 8080, 9099, 3101:

```powershell
npm run test:cloud
```

Используется только `demo-my-diary` и локальные эмуляторы — без доступа к настоящим записям. Проверяются два клиента, изоляция аккаунтов и секретов, REST, идемпотентность, конфликт обновления, отзыв доступа, полный OAuth PKCE/refresh flow и MCP через официальный клиент SDK.
